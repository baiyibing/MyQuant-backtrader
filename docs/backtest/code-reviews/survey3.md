# Backtrader 量化回测系统综述

## 一、系统概述

本系统是一个基于 **Backtrader** 框架、面向 A 股市场的量化回测平台，旨在模拟真实交易环境下的资金管理、交易规则（T+1、涨跌停）以及多策略并行回测。核心设计围绕 **全局资金池** 展开，实现了跨交易日、跨回测周期的资金统一管理和即时再投资。系统由多个高度模块化的组件构成，各司其职，协同工作。

### 主要目标
- 支持多批次选股（每日股票池来自 CSV 文件），模拟“每日定投”式买入。
- 严格遵守 A 股交易规则：T+1 锁定、涨跌停价格限制、最小交易单位（100 股）。
- 实现复杂的资金调度：涨停时自动延期、资金不足时自动补充、卖出资金即时回流再投资。
- 提供五种预设交易策略，并允许通过参数灵活调整。
- 内置资金流审计机制，确保全局资金与 Broker 现金始终保持一致。

### 核心组件及职责

| 模块 | 职责 |
|------|------|
| **backtest_main_full.py** | 主控脚本：加载数据、配置策略、启动回测、输出结果。 |
| **global_capital_manager.py** | **全局资金单例**：管理总资金池、每日投资额度、延期额度、补充资金、佣金；记录权威流水；提供审计接口。 |
| **portfolio_manager.py** | 投资组合管理器：整合涨跌停、T+1、股票状态；执行买卖订单（委托全局资金池操作）；委托策略判断买卖信号。 |
| **rolling_investment_strategy.py** | Backtrader 策略类：核心交易逻辑，包括买入时机判断、资金分配、订单创建与回滚、收盘处理。 |
| **ProfitStrategy.py** | 策略工厂：定义五种策略（version1~5）的买卖信号逻辑，支持参数覆盖。 |
| **TPlus1QueueManager.py** | T+1 规则管理器：用队列记录每笔买入，计算可卖出日期，提供可卖数量查询，FIFO 卖出。 |
| **LimitUpDownManager.py** | 涨跌停管理器：根据股票代码前缀计算涨跌停价，判断是否触及限制。 |
| **StockStatus.py** | 股票状态对象：记录成本价、持仓最高价、持仓天数、是否需要次日买入等动态信息。 |

## 二、资金管理设计（核心亮点）

### 1. 全局资金池（GlobalCapitalManager）
- **单例模式**：确保所有回测周期（多个买入日期文件）共享同一个资金池实例，资金可以跨周期复用。
- **资金构成**：
  - **主资金池** (`remaining_capital`)：总资金中未被占用的现金。
  - **延期预留资金** (`_deferred_reserved_by_date`)：因涨停而预留的资金，按到期日分类，过期自动释放。
  - **补充资金**：直接划拨自主资金池，仅用于满足最低 100 股要求，记录使用量但不单独保留池子。
- **每日投资额度**：固定每日 100 万元，但受总资金余额限制。
- **资金回流**：卖出所得立即加入主资金池，实现“即时再投资”（可跨交易日）。
- **佣金处理**：单独记录并从主资金池扣除，保持与 Broker 现金同步。

### 2. 涨停延期额度管理
- 当某只股票在买入日涨停时，将其原定分配的金额（`cash_per_stock`）从主资金池中**预留**，并记录有效期（默认 3 个交易日）。
- 预留资金按到期日汇总，在后续交易日中可被该股票专用延期额度使用。
- 延期额度按股票独立记录，使用 FIFO 顺序（按到期日）。
- 过期未使用的额度自动释放回主资金池。

### 3. 补充资金机制
- 若某只股票按平均分配金额计算后无法购买 100 股，系统会自动向全局资金池申请补充资金，补足至最小买入成本。
- 补充资金直接从主资金池划拨，仅作统计标记，不单独保留池子。
- 若后续订单失败，补充资金可回滚（`undo_supplementary_capital`）。

### 4. 资金流审计
- **权威流水**：全局资金管理器为每笔投资、回流、佣金、延期使用、补充资金等操作生成唯一交易流水号，并记录日期、类型、金额、来源。
- **T+1 记录匹配**：通过 `validate_with_authoritative_cash()` 方法，将全局流水与 T+1 管理器的买入/卖出记录逐笔核对，确保净投资额一致。
- **总资金平衡校验**：`剩余资金 + 净投资 + 预留资金 + 累计佣金 = 总资金`，差额需在容忍范围内。
- **实时验证**：每次买卖后或每日收盘时触发审计，输出详细报告。

## 三、交易规则实现

### 1. T+1 规则（TPlus1QueueManager）
- 买入记录以队列形式存储，每条记录包含买入日期、数量、价格以及**可卖出日期**（下一个交易日）。
- 卖出时按 FIFO 顺序从最早买入记录中扣除，同时记录卖出流水。
- 提供 `get_sellable_quantity()` 用于检查当日可卖出股数。
- 支持强制修正持仓（当 Broker 持仓与队列不一致时），并记录强制卖出。

### 2. 涨跌停限制（LimitUpDownManager）
- 根据股票代码前缀自动判断板块涨跌幅比例（主板 10%、创业板 20%、科创板 20%、北交所 30%、ST 5%）。
- 计算涨停价和跌停价（基于前收盘价），并实时判断当前价格是否触及。
- 买入时若涨停则不允许买入，并触发延期；卖出时若跌停则不允许卖出。

### 3. 订单执行与回滚（rolling_investment_strategy）
- 创建订单时通过 `info` 参数传递资金类型标记（`is_deferred`、`supplementary_amount`、预估成本、日期等）。
- 在 `notify_order` 中：
  - 订单完成：调用 `PortfolioManager.execute_buy/sell_order` 更新持仓，同时调用全局资金池记录投资/回流。
  - 订单失败（取消/拒单/保证金不足）：根据 `info` 中的补充资金金额调用 `undo_supplementary_capital` 回滚；延期额度仅在成交时扣除，取消时无需回滚（因预留资金未扣减）。
- 卖出订单创建前会先调用 `add_pending_sell` 记录挂单数量，避免同一股票重复卖出。

### 4. 持仓天数计算
- 基于交易日历精确计算：`持仓天数 = 交易日数 - 1`（买入当天不计入）。
- 使用 `pandas_market_calendars` 获取 SSE 日历，确保假期处理正确。

## 四、策略实现（ProfitStrategy 与策略集成）

### 策略工厂（StrategyFactory）
- 预置五种策略版本，每个版本对应一个策略类及默认参数。
- 支持通过 `custom_params` 覆盖任意参数，实现灵活调整。

### 策略逻辑简述
1. **version1**：止损 2%，回撤达到利润 50% 止盈。
2. **version2**：止损 2%，动态止盈（持仓天数越长，回撤阈值越小）。
3. **version3**：止损 4%，止盈 20%；附加开盘 10 分钟内涨停保留观察逻辑。
4. **version4**：均线策略，价格站上 10 日线买入，跌破 5 日线卖出。
5. **version5**：无止损，盈利 2% 止盈，持仓满 10 天强制卖出。

### 策略与 PortfolioManager 的集成
- `PortfolioManager` 持有策略实例，在 `should_sell` / `should_buy` 中调用策略对应方法。
- 策略方法接收当前价格、涨停跌停状态、技术指标（如均线）等参数，返回是否触发信号及原因。
- 这种设计使得交易规则（T+1、涨跌停）与纯策略信号分离，策略仅关注价格和指标，便于扩展。

## 五、回测流程详解

### 1. 数据加载（backtest_main_full.py）
- 读取 `stock_pool/` 下所有 CSV 文件，每个文件名为买入日期（如 `20251023.csv`），内容为该日待买入的股票代码列表。
- 合并所有股票代码，为每只股票加载分钟线数据（主数据）和日线数据（用于计算均线）。
- 使用交易日历计算日线数据的起始日期，确保有足够数据计算均线（至少 20 个交易日）。
- 将所有数据添加到 Cerebro，分钟线数据以股票代码命名，日线数据以 `代码_daily` 命名。

### 2. 策略初始化
- 创建全局资金管理器单例（总资金 2100 万，日投资额 100 万）。
- 创建 Cerebro，添加策略 `RollingInvestmentStrategy`，传入 `stock_buy_dict`（买入日期→股票列表映射）、全局资金管理器、策略版本及参数。
- 设置 Broker 初始现金为总资金（2100 万），佣金 0.1%。
- 添加常用分析器（Returns, SharpeRatio, DrawDown, TradeAnalyzer）。

### 3. 策略运行（RollingInvestmentStrategy.next）
- **每日更新**：更新持仓天数、市场数据，检查卖出信号（`_process_sell_orders`）。
- **开盘时段（9:30-9:45）**：处理需次日买入的股票（即前一交易日涨停延期的股票），使用其专用延期额度买入。
- **尾盘时段（14:55 后）**：处理当日正常买入：
  - 获取当日股票池（`date_to_stocks[current_date]`）。
  - 计算平均分配金额（`cash_per_stock = 当日可用常规额度 / 候选股数量`）。
  - 遍历每只股票，检查是否涨停、是否满足策略买入条件。
  - 若涨停且未跳过，则调用 `defer_quota` 预留资金，标记 `need_buy_next_day=True`。
  - 若可买入，调用 `calculate_position_size` 计算可买数量及补充资金需求，然后创建限价买单，并通过 `info` 传递资金类型。
- **收盘处理（定时器 _on_daily_close）**：取消未成交订单、执行 `end_of_day_processing`、释放过期延期额度、输出资金统计、执行审计。

### 4. 订单通知（notify_order）
- 处理订单完成、取消、拒单等状态。
- 完成时调用 PortfolioManager 的买入/卖出方法，记录交易日志，更新盈利统计。
- 失败时回滚补充资金，并移除挂单卖出计数。

### 5. 结果输出（stop）
- 计算真实最终资产（主资金池剩余 + 延期预留 + 持仓市值），与 Broker 的失真值对比。
- 输出交易统计、胜率、资金利用率、延期额度与补充资金使用情况。
- 执行最终资金审计，生成时间分析报告和资金类型使用报告。

## 六、系统亮点与优势

1. **资金管理高度真实**：全局资金池模拟了机构资金运作方式，支持延期、补充、即时再投资，贴近实战。
2. **模块化解耦**：资金管理、交易规则、策略信号、订单执行各自独立，易于维护和扩展。
3. **强审计机制**：通过权威流水与 T+1 记录逐笔匹配，确保回测过程中资金流可追溯、可验证，极大降低逻辑错误风险。
4. **灵活的策略配置**：策略工厂支持五种策略及参数覆盖，方便快速对比不同策略效果。
5. **完整的交易规则实现**：包括 T+1 队列、涨跌停价格计算、最小交易单位、交易日历等，回测结果更可信。
6. **细致的日志与统计**：内存监控、时间分析、资金类型统计等，便于调试和性能优化。

## 七、潜在问题与改进建议

### 1. 复杂度过高可能引入的 Bug
- 资金流分支较多（常规、延期、补充），且涉及跨周期回滚，容易在异常路径下出现不一致。
- **建议**：增加单元测试，覆盖各种订单状态组合；在关键操作后（如 `defer_quota`、`use_deferred_quota`）立即进行局部审计。

### 2. 延期额度有效期计算依赖交易日列表
- 若 `trading_days` 未正确传入或覆盖不全，会导致到期日计算错误，可能造成资金提前释放或过期未释放。
- **建议**：在 `__init__` 中强制要求提供交易日列表，或内部自动从 `pandas_market_calendars` 生成。

### 3. 补充资金回滚逻辑可能存在遗漏
- 在 `notify_order` 中仅回滚补充资金，但若订单部分成交（部分成交在 Backtrader 中不常见），则需要更精细的处理。
- **建议**：检查 Backtrader 是否支持部分成交，若支持需补充相应逻辑。

### 4. 资金利用率计算
- 当前 `stop` 方法中 `return_on_invested` 的计算公式可能不准确：`(real_final_portfolio_value - final_global_cash) / actually_invested_capital - 1`，其中 `real_final_portfolio_value` 包含持仓市值，而 `actually_invested_capital` 是已动用的资金（初始-剩余），两者逻辑上应比较总收益与投入本金。
- **建议**：统一使用 `(real_final_portfolio_value - initial_total_capital) / initial_total_capital` 作为总收益率，无需单独计算已动用资金收益率。

### 5. 订单创建时间记录
- `order_creation_time` 在创建订单时被设为 `None`，等待 `notify_order` 中从 `order.created.dt` 获取。但若订单立即完成，`notify_order` 中的 `creation_time` 可能无法获取到准确的创建时间（因为 `order.created.dt` 可能还未生成？）。
- **建议**：在创建订单后立即记录 `creation_time = current_datetime`，同时在 `notify_order` 中如果发现 `order_creation_time` 为 None 且 `order.created.dt` 存在，则覆盖，以获取更精确的时间戳。

### 6. 股票池重复加载
- 主脚本中先将所有股票代码合并为 `stock_buy_set` 统一加载数据，但策略内部又根据 `date_to_stocks` 筛选每日可买股票。数据加载方式合理，但注意 `stock_buy_set` 包含所有股票，即使某些股票在回测期内从未出现在买入日列表中也会被加载，浪费内存。
- **建议**：可以只加载实际出现在买入日列表中的股票，减少数据量。

### 7. 日志级别控制
- 部分日志使用了 `logger.info` 输出大量调试信息（如每个买入判断、资金分配计算），可能拖慢回测速度。
- **建议**：将高频率日志降级为 `logger.debug`，并在主脚本中通过设置日志级别为 `INFO` 控制输出。

### 8. 对 Backtrader 的依赖
- 系统大量依赖 Backtrader 的订单生命周期和定时器功能，但 Backtrader 的定时器在分钟线数据上的行为可能需要验证（`_on_daily_close` 是否在每天最后一根 K 线准确触发）。
- **建议**：在 `next` 中判断时间是否为 15:00 作为备用触发方式，代码中已包含此逻辑。

## 八、总结

本系统是一个设计精良、功能全面的 A 股量化回测框架，特别在资金管理层面实现了高度仿真和严谨的审计机制。通过模块化组合，它将交易规则、策略逻辑、资金流管理分离，既保证了灵活性，又易于维护和扩展。尽管存在一定的复杂性，但完善的日志和审计功能为调试提供了有力支持。对于希望深入研究 A 股交易策略、验证复杂资金调度逻辑的量化研究者而言，这是一个非常优秀的参考实现。未来可通过增加单元测试、简化部分分支逻辑，进一步提升系统的健壮性和易用性。
