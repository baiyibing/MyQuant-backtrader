# 订单生命周期详解：从决策到成交/取消的完整流程

在 Backtrader 与自定义资金管理框架中，订单的生命周期遵循标准的事件驱动模式，但通过 `PortfolioManager`、`GlobalCapitalManager`、`TPlus1QueueManager` 等组件扩展了资金管理、T+1 规则、涨停延期等复杂逻辑。下面以买入订单为例（卖出订单类似），详细阐述各阶段的过程，并重点说明 `PortfolioManager` 中维护的关键状态变量如何协同工作。

## 1. 订单决策阶段（`next()` 方法）

### 1.1 信号触发
策略在 `next()` 中处理每日逻辑，其中 `_process_buy_orders()` 负责检查是否符合买入条件。根据当前时间，分为两种情况：
- **次日开盘买入**（9:30-9:45）：调用 `_process_next_day_buy_orders()`，针对 `need_buy_next_day=True` 且拥有可用延期额度的股票。
- **正常买入**（14:55后）：调用 `_process_normal_buy_orders()`，针对当日候选股票。

### 1.2 条件检查
每只股票需通过一系列检查，这些检查充分利用了 `PortfolioManager` 维护的状态：

- **是否有未完成订单**：调用 `_can_buy()`，它检查 `self.orders[stock]` 是否为 `None`，确保同一时间只有一笔未完成订单。
- **T+1 规则是否允许买入**：调用 `portfolio_manager.can_trade_tplus1(stock, 'BUY', current_datetime)`。该方法内部会检查：
  - `stock not in self.today_buy_stocks`：确保当日未买入过该股票（防止重复买入）。
  - `not status.has_buy_order`：确保股票状态中没有正在进行的买入订单（该标记在订单创建时设为 `True`，订单完成或取消时设回 `False`）。
- **是否已标记为次日买入**（仅正常买入）：`status.need_buy_next_day` 为 `True` 的股票应跳过，由延期流程处理。
- **是否涨停或接近涨停**：通过 `limit_manager.is_limit_up()` 和 `is_near_limit_up()` 判断。若涨停且未设置跳过，则调用 `handle_limit_up_deferral()` 将计划资金转为延期额度，不创建订单。
- **策略买入信号**：调用 `portfolio_manager.should_buy()`，由具体策略版本决定是否买入。

### 1.3 资金计算
通过 `portfolio_manager.get_buy_size()` 计算可买入数量及所需补充资金。该方法根据分配模式（`equal`/`force_min`/`dynamic`）和是否延期，返回 `(size, supplementary_needed)`。延期买入时不允许补充资金，且使用整数分计算确保成本不超过延期额度。

### 1.4 记录决策时间
将当前时间存入 `self.order_decision_time[stock]`，用于后续时间分析。

## 2. 订单创建与提交（`buy()` / `sell()`）

### 2.1 订单参数
- **数据源**：`data`（对应股票的分钟线数据）。
- **数量**：`size`（计算得到的股数）。
- **价格**：
  - 正常买入：市价单（`price=0`，`exectype=bt.Order.Market`）。
  - 延期买入：限价单（`price=current_price`，`exectype=bt.Order.Limit`）。
- **有效期**：`valid=bt.Order.DAY`（当日有效）。
- **额外信息**：通过 `info` 字典传递自定义数据，如 `{'is_deferred': True/False, 'stock': code, 'date_str': current_date_str}`。这些信息将在 `notify_order` 中读取，用于区分资金类型。

### 2.2 更新订单相关状态
在调用 `buy()`/`sell()` 之前或之后，策略需要更新 `PortfolioManager` 中的状态，以确保后续检查的准确性：

- **对于买入订单**：应设置 `status.has_buy_order = True`（虽然当前代码中未显式设置，但应在创建订单后立即设置，或在 `order_info` 中标记并由 `notify_order` 统一处理）。
- **对于卖出订单**：
  - 调用 `portfolio_manager.add_pending_sell(stock, size)`，增加挂单卖出计数，避免后续卖出超过可卖数量。
  - 设置 `status.has_sell_order = True`。

### 2.3 订单提交
调用 `self.buy()` 或 `self.sell()` 后，订单被提交给 Backtrader 的 Broker，状态变为 `Submitted`。策略将订单对象保存在 `self.orders[stock]` 中，以备后续引用。

## 3. 订单状态流转与通知（`notify_order()`）

Backtrader 会在订单状态变化时回调 `notify_order()`。关键状态处理如下：

### 3.1 订单完成（`order.status == order.Completed`）
- **获取时间**：
  - 决策时间：从 `self.order_decision_time.get(stock_name)` 获取。
  - 创建时间：优先使用 `order.created.dt`（精确到微秒），否则使用当前时间。
  - 执行时间：使用 `order.executed.dt` 或当前时间。
- **佣金处理**：读取 `order.executed.comm`，累计到 `self.total_commission`，并通过 `portfolio_manager.record_commission()` 同步到全局资金池。
- **方向判断**：
  - **买入成交**：调用 `portfolio_manager.execute_buy_order(stock_name, price, size, order_executed_time, is_deferred)`。
    - 内部执行资金扣除（延期额度或常规+补充）、T+1 记录添加、更新股票状态（详见第4节）。
    - 成功后，策略调用 `self.log_trade()` 记录交易并更新盈利记录；同时应清除 `has_buy_order` 标记（`status.has_buy_order = False`）。
    - 若失败（资金操作异常），触发 `RuntimeError` 终止回测（因已回滚）。
  - **卖出成交**：调用 `portfolio_manager.process_sell_order_execution(stock_name, price, size, order_executed_time)`。
    - 内部移除挂单、执行 T+1 卖出、记录资金回流、更新持仓状态（详见第4节）。
    - 成功后记录交易日志，并清除 `has_sell_order` 标记。
- **清理时间记录**：删除 `self.order_decision_time` 和 `self.order_creation_time` 中对应股票的记录。
- **移除订单引用**：`self.orders[stock_name] = None`。

### 3.2 订单取消/拒绝/保证金不足（`Canceled`, `Margin`, `Rejected`）
- **卖出订单的挂单清理**：若为卖出订单，计算未成交部分（`remaining_size = order.created.size - abs(order.executed.size)`），调用 `portfolio_manager.remove_pending_sell()` 移除挂单计数。同时清除 `has_sell_order` 标记。
- **买入订单的标记清理**：若为买入订单，清除 `has_buy_order` 标记。
- **记录取消事件**：将取消信息（股票、剩余数量、价格、原因）追加到 `self.cancel_log`，用于每日报告。
- **时间分析**：若记录了决策时间，计算总延迟并输出警告。
- **清理时间记录**：删除对应的决策时间和创建时间。
- **移除订单引用**：`self.orders[stock_name] = None`。

## 4. 成交后的资金处理与状态更新

### 4.1 买入成交处理（`execute_buy_order`）
```python
# portfolio_manager.py
def execute_buy_order(self, stock_code, price, size, executed_time, is_deferred=False):
    cost = price * size
    if is_deferred:
        # 1. 扣减延期额度（FIFO）
        success_use, used, used_details = self.global_capital_manager.use_deferred_quota(...)
        # 2. 记录投资（延期）
        success_record, txn_id = self.global_capital_manager.record_investment(..., is_deferred=True)
    else:
        # 计算所需补充资金
        available_normal = self.global_capital_manager.get_available_investment(..., include_deferred=False)
        supplementary_needed = max(0, cost - available_normal)
        # 记录投资（常规+补充）
        success_record, txn_id = self.global_capital_manager.record_investment(..., supplementary_amount=supplementary_needed)
    # 更新股票状态、持仓字典等
```
- **原子化**：先添加 T+1 记录（`tplus1_manager.add_buy_record`），再执行资金操作。若资金操作失败，立即回滚 T+1 记录和已记录的投资流水。
- **延期额度使用**：`use_deferred_quota` 按到期日顺序扣减，返回使用明细，便于后续可能回滚。
- **补充资金**：动态计算，通过 `record_investment` 一并从主资金池扣除（补充资金也来自主资金池，但单独统计）。
- **状态更新**：
  - 更新 `StockStatus` 中的成本价、最高价、买入日期。
  - 将股票加入 `today_buy_stocks`：`self.today_buy_stocks.add(stock_code)`。
  - 更新快速持仓字典 `position_size[stock_code]` 为 T+1 管理器返回的最新总持仓。
  - 此时策略层面的 `has_buy_order` 应在 `notify_order` 中被清除。

### 4.2 卖出成交处理（`process_sell_order_execution`）
```python
# portfolio_manager.py
def process_sell_order_execution(self, stock_code, price, size, executed_time):
    # 1. 移除挂单计数
    self.remove_pending_sell(stock_code, size)
    # 2. T+1 队列出队
    actual_sold = self.tplus1_manager.execute_sell(stock_code, size, price, executed_time)
    # 3. 若实际卖出数量不足，强制修正
    if actual_sold < size:
        self.tplus1_manager.force_remove_position(...)
    # 4. 获取最新持仓信息，更新状态
    new_position_info = self.tplus1_manager.get_position_info(stock_code)
    remaining_quantity = new_position_info['total_quantity']
    status = self.get_stock_status(stock_code)
    if remaining_quantity > 0:
        self.position_size[stock_code] = remaining_quantity
        status.cost_price = new_position_info['avg_price']
    else:
        status.reset_after_sell()
        self.position_size.pop(stock_code, None)
    # 5. 记录今日卖出
    self.today_sell_stocks.add(stock_code)
    # 6. 记录资金回流
    self.global_capital_manager.record_reflow(proceeds, executed_time, stock_code)
    # 7. 更新投资组合价值
```
- **挂单清理**：`remove_pending_sell` 确保 `pending_sells` 与实际成交一致。
- **T+1 队列**：`execute_sell` 按 FIFO 原则从持仓队列中扣除，返回实际卖出的数量。若队列不足（理论上不应发生），调用 `force_remove_position` 强制修正。
- **资金回流**：`record_reflow` 立即将资金加入主资金池，实现跨交易日即时复用。
- **状态更新**：
  - 若全部卖出，重置股票状态；否则更新成本价。
  - 将股票加入 `today_sell_stocks`。
  - 策略层面的 `has_sell_order` 应在 `notify_order` 中被清除。

## 5. 取消订单的清理

### 5.1 主动取消（收盘时）
策略通过定时器（每日 15:00）触发 `_on_daily_close()`，遍历所有未完成订单并调用 `self.cancel(order)`。取消后，`notify_order` 会收到 `Canceled` 状态，执行上述 3.2 节的清理逻辑。

### 5.2 被动取消（Broker 拒绝）
若订单因价格、保证金等原因被拒绝，同样进入 `Canceled`/`Rejected` 状态，按 3.2 处理。

### 5.3 关键点
- **资金回滚**：取消订单不会回滚资金，因为资金只在成交时扣除。未成交订单不会占用资金（Backtrader 的 Broker 会在订单取消后释放冻结资金）。
- **挂单计数**：对于卖出订单，必须通过 `remove_pending_sell` 移除挂单计数，否则会导致后续可卖数量计算错误。
- **订单标记**：必须清除 `has_buy_order` 或 `has_sell_order`，以便后续再次下单。

## 6. 收盘处理与订单最终化

在 `_on_daily_close()` 中，除了取消订单，还执行：
- **资金审计**：调用 `portfolio_manager.validate_cash_consistency()` 核对全局流水与 T+1 记录。
- **每日报告**：输出当日交易流水、持仓、资金统计。
- **重置状态**：
  - 清空 `pending_sells`（所有未成交订单已被取消，挂单计数应归零）。
  - 重置 `_daily_allocated_cash` 和 `_supplementary_capital_used_today`，准备次日。
  - 注意：`today_buy_stocks` 和 `today_sell_stocks` 已在每日开盘时清空（`update_market_data` 中），这里无需重复。

## 7. 回滚机制确保一致性

在订单处理的关键节点，系统实现了原子化操作与回滚：

- **买入成交的原子化**：`execute_buy_order` 中的 `try...except` 确保 T+1 记录、延期额度扣减、投资记录三者全部成功，否则回滚所有已执行步骤。
- **延期额度回滚**：`undo_deferred_quota` 恢复已使用的延期额度（按原到期日或重新计算）。
- **投资记录回滚**：`undo_investment` 根据资金来源返还资金并冲销统计。
- **T+1 记录回滚**：`tplus1_manager.undo_last_buy` 删除最近买入记录。

## 8. 订单生命周期图示

```plaintext
[策略 next] 
    │
    ├─ 检查信号 → 决策时间记录
    │   使用 today_buy_stocks, has_buy_order 等检查 T+1
    │
    └─ 调用 buy()/sell() → 订单创建 (info 传递 is_deferred 等)
         │   ├─ 买入：设置 has_buy_order = True
         │   └─ 卖出：add_pending_sell() + 设置 has_sell_order = True
         ↓
[Broker] 订单状态流转
    ├─ Submitted/Accepted (不触发 notify)
    ├─ Completed → notify_order
    │    ├─ 佣金记录
    │    ├─ 买入: execute_buy_order (资金扣除, T+1 记录, 状态更新)
    │    │   └─ 更新 today_buy_stocks, position_size, 清除 has_buy_order
    │    └─ 卖出: process_sell_order_execution (资金回流, T+1 出队)
    │        └─ 移除 pending_sell, 更新 position_size/today_sell_stocks, 清除 has_sell_order
    │
    └─ Canceled/Rejected/Margin → notify_order
         ├─ 移除挂单卖出计数 (若卖出) + 清除 has_sell_order
         ├─ 清除 has_buy_order (若买入)
         ├─ 记录取消日志
         └─ 清理时间记录
```

## 9. 关键状态变量总结

`PortfolioManager` 维护了多个关键状态，确保交易符合 T+1 规则并防止重复下单：

| 状态变量 | 类型 | 作用 | 更新时机 |
|---------|------|------|----------|
| `today_buy_stocks` | `set()` | 记录当日已买入股票，防止同一股票日内重复买入 | 买入成交后添加；每日开盘清空 |
| `today_sell_stocks` | `set()` | 记录当日已卖出股票（目前用于统计） | 卖出成交后添加；每日开盘清空 |
| `position_size` | `Dict[str, int]` | 快速查询当前持仓股数，用于价值计算和持仓天数更新 | 买入/卖出成交后从 T+1 管理器获取最新值更新 |
| `pending_sells` | `Dict[str, int]` | 记录已提交但未成交的卖出订单总股数，避免超卖 | 创建卖出订单前增加；订单成交/取消后减少 |
| `has_buy_order` (在 `StockStatus` 中) | `bool` | 标记股票是否有未完成的买入订单 | 创建买入订单时设为 `True`；订单完成/取消时设回 `False` |
| `has_sell_order` (在 `StockStatus` 中) | `bool` | 标记股票是否有未完成的卖出订单 | 创建卖出订单时设为 `True`；订单完成/取消时设回 `False` |

这些状态与 T+1 管理器、资金管理器紧密协作，共同构建了稳健的交易执行框架，确保回测结果的可靠性和可重复性。
