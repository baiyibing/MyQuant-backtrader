## 1. 单例模式
`GlobalCapitalManager` 采用单例模式，确保整个回测过程中（多个买入日期文件）所有策略实例共享同一个资金池实例。资金可以跨交易日、跨回测周期复用，例如当日卖出回流的资金可在后续任何交易日立即使用。

```
[GlobalCapitalManager 单例]
    │
    ├─ [常规可用现金 available_regular_capital] ── 初始为总资金，包含回流资金
    │       │
    │       └─ 所有投资支出（常规/延期/补充）从此扣除
    │
    ├─ [延期预留资金 _deferred_reserved_by_date] ── 按到期日分类，到期释放回主池
    │       │
    │       └─ 每笔额度关联具体股票，有效期内可被该股票使用
    │
    └─ [补充资金统计 _supplementary_capital_used] ── 仅作统计标记，资金直接划拨自主资金池
```

## 2. 资金构成
- **主资金池（常规可用现金）**：由 `available_regular_capital` 表示，初始为总资金（如2100万元）。它包含所有未被占用的现金，以及卖出回流资金。所有投资支出（常规、延期、补充）均从主资金池扣除。
- **延期预留资金**：因股票涨停或接近涨停而预留的资金，按到期日分类存储在 `_deferred_reserved_by_date` 中。每笔延期额度关联具体股票，在有效期内（交易日天数）可被该股票使用，到期自动释放回主资金池。
- **补充资金**：**无独立资金池**，仅作为统计标记记录在 `_supplementary_capital_used` 中。补充资金直接划拨自主资金池，用于以下两种情况：
  - **主动触发**：在 `force_min` 分配模式下，若分配给某股票的常规资金不足以购买100股，则强制买入一手，所需差额从主资金池补充。
  - **被动触发**：任何常规买入订单成交时，若实际成交金额超过当前常规可用现金（例如因价格波动或之前订单已消耗部分常规额度），则从主资金池补充差额。
  
  补充资金 **不占用每日100万元常规投资额度**，但会减少主资金池余额。

## 3. 每日常规投资额度
- **每日上限**：固定100万元，受主资金池余额限制（实际可用 ≤ 日限额且 ≤ 主资金池余额）。
- **分配模式**（通过策略参数 `allocation_mode` 切换）：
  1. **等额分配（equal）**：每日开盘时将当日可用常规额度平均分配给当日所有候选股票。若某股票分配额不足以购买100股，则放弃该股票（`force_min=False`）。
  2. **强制一手（force_min）**：同样进行等额分配，但在调用 `get_buy_size` 时传入 `force_min=True`。若分配金额不足100股，则强制返回100股并计算所需补充资金。该模式确保每只候选股票至少建仓一手。
  3. **动态按需分配（dynamic）**：每日开盘或买入前重新计算分配。获取所有候选股票的当前价格（使用当前K线收盘价），计算每只股票买入100股所需资金。若总需求 ≤ 当日可用常规额度，则每只股票分配一手所需金额；若总需求超过可用额度，则按比例缩减股数（向下取整至100的倍数），并将分配金额存入 `dynamic_allocations` 字典。遍历时使用该金额调用 `get_buy_size`（此时 `force_min=False`），分配已考虑资金上限，理论上不触发补充资金，但实际成交价波动仍可能触发。

- **订单类型**：常规买入使用 **市价单**（`bt.Order.Market`，价格设为0），以确保成交。涨停已在逻辑中拦截并转为延期，因此市价单未成交的可能性极低；若出现未成交，收盘时会被取消，暂不进一步处理。

- **下单前检查逻辑**（`_process_normal_buy_orders`）：

```
[常规买入处理 (时间 ≥ 14:55)]
    │
    ├─ 检查 can_invest_today() → 若无可投额度则退出
    │
    ├─ 获取 available_normal → 若 ≤0 则退出
    │
    └─ 遍历当日候选股票列表
         │
         ├─ 股票基础检查（数据存在/无订单/T+1允许/买入日匹配/未标记延期）
         │    └─ 若失败 → 继续下一只股票
         │
         ├─ 价格异常处理
         │    ├─ 若接近涨停（当前价 ≥ 涨停价×(1-阈值)）且 defer_on_near_limit_up=True
         │    │   → 调用 handle_limit_up_deferral 将计划金额转为延期预留，跳过买入
         │    ├─ 若涨停且 skip_limit_up=False
         │    │   → 同样调用 handle_limit_up_deferral 转为延期预留，跳过买入
         │    └─ 若涨停且 skip_limit_up=True
         │        → 直接跳过（不延期）
         │
         ├─ 调用 should_buy() → 若无买入信号则跳过
         │
         ├─ 根据分配模式获得 allocated_cash
         │    ├─ equal/force_min: 使用开盘计算的 cash_per_stock
         │    └─ dynamic: 使用 dynamic_allocations.get(stock, 0)
         │
         ├─ 调用 get_buy_size(allocated_cash, force_min) → 返回 (size, supplementary_needed)
         │    （注：supplementary_needed 仅在成交后实际计算，此处返回值仅用于日志）
         │
         └─ 若 size ≥ 100 → 创建市价单，记录决策时间，设置订单info（is_deferred=False等）
```

## 4. 每日延期投资额度
- **来源**：股票涨停或接近涨停（满足阈值）时，原计划用于该股的常规额度转为延期预留，按交易日有效期存入对应股票的延期记录。
- **订单类型**：延期买入使用 **限价单**（`bt.Order.Limit`），限价为当前价格（次日开盘价），以确保成本不超出延期额度。
- **数量计算**：在 `get_buy_size` 中对延期买入采用整数分计算，并增加验证循环，确保按当前价格计算的股数成本 ≤ 该股可用延期额度。若计算后不足100股，则放弃买入（延期投资 **不启用补充资金**）。
- **未成交处理**：若限价单因价格变动无法成交，额度不会扣减（仅在成交时通过 `use_deferred_quota` 扣除），延期额度保持不变，留待后续交易日继续使用，直至过期释放。
- **有效期**：通过 `_calculate_expiry_date` 基于交易日历计算到期日，过期自动释放回主资金池。

- **下单前检查逻辑**（`_process_next_day_buy_orders`）：

```
[次日开盘买入处理 (9:30-9:45)]
    │
    └─ 遍历所有股票
         │
         ├─ 检查 need_buy_next_day = True? 若否 → 跳过
         │
         ├─ 获取该股票当日可用延期额度 deferred
         │    ├─ 若 deferred ≤ 0 → 清除 need_buy_next_day，跳过
         │    └─ 若 deferred < 100 * 当前价 → 清除标记，跳过
         │
         ├─ 检查 T+1 规则是否允许买入 → 若否，跳过
         │
         ├─ 价格异常处理
         │    ├─ 若接近涨停且 defer_on_near_limit_up=True → 保留延期额度，本次跳过
         │    ├─ 若涨停且 skip_limit_up=False → 保留延期额度，本次跳过
         │    └─ 若涨停且 skip_limit_up=True → 清除 need_buy_next_day，跳过
         │
         ├─ 调用 should_buy() → 若无买入信号则跳过
         │
         ├─ 调用 get_buy_size(is_deferred=True, allocated_cash=deferred) → 返回 size
         │
         └─ 若 size ≥ 100 → 创建限价单（价格=开盘价），记录决策时间，设置订单info is_deferred=True
```

## 5. 资金回流
卖出成交后，通过 `record_reflow` 将所得资金（扣除佣金前的金额） **立即加入主资金池**，实现即时再投资。回流资金可跨交易日使用，不受当日卖出时间限制。

```
[卖出订单成交]
    │
    └─ [process_sell_order_execution]
         │
         ├─ 移除挂单卖出数量 (remove_pending_sell)
         │
         ├─ T+1 队列出队 (execute_sell)
         │
         ├─ 更新持仓状态 (position_size, StockStatus)
         │
         ├─ [record_reflow] ── 将卖出金额加入 available_regular_capital
         │    ├─ 主资金池增加
         │    └─ 记录回流统计 _daily_reinvestment_inflow
         │
         └─ 更新投资组合价值
```

## 6. 佣金处理
每笔交易成交后，佣金通过 `record_commission` 从主资金池扣除，并累计到 `total_commission` 中。此举保持主资金池余额与 Broker 现金一致（Broker 也会在订单执行时自动扣除佣金）。

## 7. 资金一致性审计
通过 `validate_with_authoritative_cash` 方法，利用权威交易流水（`_transaction_ledger`）与 `TPlus1QueueManager` 中的交易记录进行逐笔或快速汇总核对，确保资金池状态与所有交易记录严格一致，支持调试和异常定位。

## 8. 回滚与异常处理
为确保资金操作的原子性和数据一致性，系统在多个层面实现了回滚机制：

- **投资记录撤销**：`undo_investment(transaction_id)` 用于撤销已记录的投资。该方法根据资金来源（`NORMAL`、`SUPPLEMENTARY`、`DEFERRED`）分别处理：
  - `NORMAL`：返还资金并冲销 `investment_records`。
  - `SUPPLEMENTARY`：返还资金并冲销 `_supplementary_capital_used`。
  - `DEFERRED`：仅警告，延期额度的恢复需调用专门的 `undo_deferred_quota`。
  撤销操作会添加反向流水（`INVEST_CANCEL`），保持审计完整性。

- **延期额度撤销**：`undo_deferred_quota(stock_code, date_str, amount, used_details)` 用于撤销已使用的延期额度。若提供了 `used_details`（由 `use_deferred_quota` 返回），则按原到期日恢复预留；否则按默认有效期重新计算到期日并恢复。同时从 `_deferred_quota_used` 中减去已使用金额，并添加反向流水。

- **T+1 记录撤销**：`TPlus1QueueManager.undo_last_buy(stock_code, record_id)` 用于撤销尚未被卖出的买入记录。当买入订单成交但后续资金记录失败时，调用此方法回滚 T+1 队列，确保持仓记录与资金操作一致。

- **买入订单的原子化处理**：在 `PortfolioManager.execute_buy_order` 中，资金扣除、T+1 记录添加、投资记录三者被封装在一个原子操作内。任何步骤失败都会触发回滚：

```
[execute_buy_order]
    │
    ├─ 判断是否为延期买入 (is_deferred)
    │
    ├─ 延期买入分支
    │    ├─ 调用 use_deferred_quota 扣减延期额度
    │    ├─ 若扣减失败 → 抛出异常
    │    └─ 调用 record_investment(is_deferred=True)
    │         ├─ 若成功 → 更新状态，返回成功
    │         └─ 若失败 → 调用 undo_deferred_quota 恢复额度，抛出异常
    │
    └─ 常规买入分支
         ├─ 计算所需补充资金 (supplementary_needed) = max(0, 实际成交金额 - 当前可用常规现金)
         ├─ 调用 record_investment(supplementary_amount)
         │    ├─ 若成功 → 更新状态，返回成功
         │    └─ 若失败 → 调用 tplus1_manager.undo_last_buy 回滚 T+1 记录，抛出异常
```

- **卖出订单的挂单清理**：当卖出订单被取消或拒绝时，策略的 `notify_order` 中调用 `portfolio_manager.remove_pending_sell` 移除挂单计数，但资金已在成交时回流，取消订单无需回滚资金。若订单部分成交，则只移除未成交部分的挂单。

- **收盘清理**：每日收盘时，通过定时器触发 `_on_daily_close`，取消所有未成交订单，释放可能冻结的资金。同时清空 `pending_sells`，为次日做好准备。

- **延期买入订单取消**：当延期买入订单因任何原因被取消时，策略在 `notify_order` 中检测到订单为延期买入且被取消，会重新将对应股票的 `need_buy_next_day` 标记设为 `True`。此举确保该股票的延期额度在剩余有效期内可继续尝试买入，直至成功或过期释放。额度本身不受影响，仍在预留池中等待下次尝试。

```
[订单状态流转 (notify_order)]
    │
    ├─ Completed
    │    ├─ 佣金记录
    │    ├─ 买入: execute_buy_order (原子操作)
    │    │   └─ 更新 today_buy_stocks, position_size, 清除 has_buy_order
    │    └─ 卖出: process_sell_order_execution
    │        └─ 移除 pending_sell, 更新 position_size/today_sell_stocks, 清除 has_sell_order
    │
    └─ Canceled/Rejected/Margin
         ├─ 卖出: 移除挂单卖出计数 + 清除 has_sell_order
         ├─ 买入: 清除 has_buy_order
         ├─ 记录取消日志
         ├─ 延期买入: 恢复 need_buy_next_day = True  (新增)
         └─ 清理时间记录
```

上述回滚机制与审计流水紧密结合，确保任何异常发生后资金池状态仍可追溯和恢复，保障回测结果的可靠性和可重复性。

## 9. 回测终止处理

回测运行终止分为正常终止和异常终止两种情况，系统在两种情况下均确保资金管理状态的可追溯性和一致性。

### 9.1 正常终止

当回测完成所有数据点后，Backtrader 会自动调用策略的 `stop` 方法。`stop` 方法执行以下关键步骤：

1. **最终收盘处理**：若最后交易日尚未执行收盘处理（例如数据最后一天未触发定时器），则显式调用 `_on_daily_close(final_datetime)`，取消所有未成交订单、释放冻结资金，并执行资金一致性验证。
2. **最终资金一致性验证**：调用 `portfolio_manager.validate_cash_consistency(final_datetime)` 对全局资金流水与 T+1 记录进行权威核对，确保回测结束时资金池状态与所有交易记录严格一致。
3. **统计报告输出**：
   - 从 `PortfolioManager` 获取权威投资组合价值、现金余额、持仓信息。
   - 从 Broker 获取参考数据，计算差异并输出警告（若差异超过 1 元）。
   - 计算基于权威数据的收益率（总收益率、已动用资金收益率）。
   - 输出交易绩效统计（胜率、交易次数等）。
   - 输出全局资金池最终状态（包括延期额度、补充资金使用明细）。
4. **现金一致性校验**：再次调用 `_check_cash_consistency` 核对 Broker 现金与资金池总现金的一致性。
5. **时间分析报告**（若启用）：输出决策到创建、创建到执行的延迟统计。
6. **资金类型使用报告**：统计延期额度、补充资金、正常投资的使用笔数和总额。

正常终止时，系统会完整地报告回测结果，并验证资金一致性，为用户提供可信的最终状态。

### 9.2 异常终止

当发生无法恢复的严重错误时，策略会主动终止回测，常见的异常终止情况包括：

- **资金不一致**：在 `notify_order` 中，若延期买入或常规买入订单成功成交，但 `PortfolioManager.execute_buy_order` 返回 `False`（表示资金记录失败且已回滚），策略会立即 `raise RuntimeError(f"资金不一致，终止回测: {stock_name}")`，并输出详细的订单信息（成交价、数量、佣金、订单状态、订单 info），帮助定位问题。
- **未捕获的异常**：若策略的 `next` 方法或其他回调中抛出未被捕获的异常（例如除零错误、属性错误等），Backtrader 会捕获并终止回测。此时资金管理器的状态停留在最后一次成功操作之后，但可能因缺少最终收盘处理而存在未取消订单。用户可通过日志查看异常堆栈，定位错误原因。
- **外部干预**：用户手动中断回测（如 KeyboardInterrupt）也会导致回测终止，此时资金状态可能处于中间状态，需用户自行判断。

异常终止时，系统不会执行正常的收盘处理和统计报告，但会在日志中记录错误细节（如资金不一致时打印订单信息）。为便于问题排查，建议用户在回测代码外层捕获异常并输出资金池摘要。

### 9.3 终止后状态检查

无论正常或异常终止，用户均可通过以下方式检查资金管理器的最终状态：
- 调用 `portfolio_manager.get_summary()` 获取资金池摘要。
- 调用 `portfolio_manager.get_cash_flow_breakdown()` 获取资金流明细。
- 直接检查 `global_capital_manager` 的流水记录和预留资金。

这些接口为终止后的审计和调试提供了充分支持。
