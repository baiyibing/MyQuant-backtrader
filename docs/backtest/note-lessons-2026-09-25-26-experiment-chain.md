## 一、断言纪律（最贵的一课）

**教训 1：否定性断言必须先查代码/产物，不许凭"上下文里没见到"就说"没有"。**

- 症状：两次对用户说"CSV 做不了真 dropout"/"引擎不校验 bars hash"，均为错。用户亲手做过的东西被否定。
- 根因：只看了 tracker 一句带语境的话、grep 一处没扫到就下全称结论。
- **纪律**：说"没有/不存在/从未"之前，必须给出否定性搜索的证据（搜了什么、范围多大）；查不到就明说"待查"。引用文档结论时必须带该结论的时效与语境。
- **纪律**：用户对其亲手实验的记忆，默认优先于 agent 的推断。冲突时去翻代码，不先纠正用户。

**教训 2：数字必须带配置标签。** +2.19%（五闸全叠）、+103.83%（旧 sizing 语义）、+59.1%（占位价退化篮子）——三个数字都真实，都被误读过。
- **纪律**：报任何回测数字必须同时报：池来源、sizing 模式、闸位、成交域、数据窗口。五要素不全的数字不许单独出现在结论里。

**教训 3：结论要打来源标签。** [原文]（产物逐字读出，附路径）/[推论]（写明推理链）/[存疑]（明说没查实）。关键决策（合 PR、开专题）前的依据必须可复核。

## 二、复刻实验的配置纪律

**教训 4：复刻历史实验 = 从产物回显逆向出配置清单，逐项核对，不许凭记忆拼。**

- 症状：复刻 103% 锚漏了 `--daily-quota 100000000`（默认 100 万吃掉）→ 复跑只剩 +6.90% → 又误诊为"代码回归"。
- 根因：历史命令没有落盘，配置靠重构；summary 回显里缺决定性参数。
- **纪律**：
  1. 复刻前先列**配置清单表**（每项注明出处：产物回显/文档/代码定义），缺出处的不许动手；
  2. 优先**行为级验证**：先用同输入栈复跑一次基线引擎（秒级到分钟级），对上原产物数字再开始正式实验——本次若先做了这步，quota 问题在 12 秒内就会暴露；
  3. 看到行为差异，**先怀疑自己的配置，再怀疑引擎**——比例是 10:1。

**教训 5：回显要携带全部决定性参数。** `daily_quota` 不在 summary 回显里，事故只能靠逐笔 diff 反推。
- **纪律**：新开关合入时，同步检查它是否出现在产物回显/summary 中；不在，就补。

## 三、平台与环境纪律

**教训 6：字节级断言跨平台/跨版本必炸，要有防护。**
- 症状：pandas ns/ms、autocrlf 咬 schema 与 fixture、CSV float 格式化 Windows/Linux 不同——三批"CI 过本地挂"。
- **纪律**：`.gitattributes` 对字节钉死类文件（schema/fixture/golden）强制 `eol=lf`（已落地）；字节基线测试的期望值构造必须做版本无关归一（如 `.as_unit("ns")` 双侧归一）；数据依赖（pandas 等）在 CI 与开发机**锁同一版本**（已锁 3.0.6）。

**教训 7：依赖版本统一是集群纪律。** CI/VM/4090 三处 pandas 不同 → 同一测试三种结果，互相消耗信任。
- **纪律**：升级数据栈版本 = 一个正式 PR（改 requirements + 全量测试 + 通知所有机器同步），不许单机悄悄升。

## 四、长跑实验纪律

**教训 8：超过 30 分钟的跑必须先探针再等待。**
- 症状：s12 X-01 卡 identities 校验 4.5 小时（逐行 iterrows），傻等了三轮重跑。
- **纪律**：长跑发车后 30 分钟未见输出 → py-spy dump 看栈在哪（一次采样 5 秒），区分"健康计算"与"热点低效"；热点是纯 Python 逐行循环的，先向量化再跑，不等。
- **纪律**：向量化前先 py-spy 定位真热点（本次是 `_validate_frame` iterrows 和 ymd/hm 逐行 list()），不凭直觉猜。修完跑域测试确认语义不变。
- **纪律**：同一实验重跑 ≥2 次仍未出数 → 强制停下来做根因分析，禁止"再跑一次试试"。

**教训 9：双执行器禁止。** 一台机器同一时段只允许一个 agent 跑写盘类任务；发车前 `wmic`/`Get-Process` 核对。Grok bot 与 zcode 曾在同一目录撞车（B 半成品被隔离返工）。

**教训 10：磁盘水位是长跑的前置检查项。** portfolio 跑 5 小时死于 ENOSPC。
- **纪律**：发车 >1h 的任务前 `df -h`；写盘量 >10GB 的任务预估并确认余量；D 盘 <20G 时先清理再发车。

## 五、AI 协作纪律（多 agent 分工）

**教训 11：文档是命令。** 交接文档里一行 stale 配置（scores=merged）直接把 Grok bot 带进沟里。
- **纪律**：交接文档里的输入/路径/命令行视为**可执行规格**，写的时候按"会被照抄执行"的标准写；发现错误第一时间勘误 PR，并在 PR 里 @ 所有会照抄的执行方。

**教训 12：谁审的谁对版本负责。** #211 合入的是 Kimi 重写版，我分支上的窗口修复没跟着进——三方（我/Kimi/Grok bot）各改一块时，**合入前必须 diff 确认"合入的版本包含谁修的什么"**，缺的列成清单转交。

**教训 13：修复专题的多开关时代，兼容矩阵是 plan 的必填节。** 每个 plan 必须列出：与既有修复开关、策略书、引擎入口的所有组合，逐一裁决"允许/拒绝/不适用"。

## 六、数据质量认知

**教训 14：真湖数据的三类已知偏差，X-01 类实验发车前必查**：
1. **前复权 parquet 历史比 raw 短且末日滞后**（002870.SZ 案例：前复权 2017 起、滞后 3 周）→ 域对称检查必须限定重叠窗口；
2. **变比例票占多数**（s12 池 2261 只中 1601 只窗口内除过权）→ 跨域换算实验**发车前先跑比例类型扫描**（脚本 `_scan_ratio_types_20260926.py`），把 B10 证书准备好，而不是跑到一半撞墙；
3. **停牌行 0 价** → per-symbol skip，不整批拒（已按行业标准落地）。

**教训 15：fail-closed 是特性，不是障碍。** 资金不足报错、变比例拒跑、日期集不一致拦截——每次 fail-closed 都在阻止一个"悄悄算错"。遇到 fail-closed 先查它拦得对不对，不对才改检查；拦得对就补数据/补证书，不改检查。

## 七、扫描/工具脚本自检

**教训 16：一次性脚本也要过一遍最小编译检查。** 本日扫描脚本三个低级 bug（`dividend_type=raw` 应为 `none`、`frames["raw"]` 键不匹配、`Path()` 包装缺失），浪费三轮往返。
