## 背景

用户怀疑本地从 QMT 数据计算的"赢筹率"（`cyqk_c`，即获利筹码比例）与券商（同花顺/通达信）显示值存在偏差，要求系统性地审查问题根因并量化偏差大小。

## 第一阶段：现状审查（已完成初步探索）

### 本地赢筹算法架构

- **核心来源**：`qlib_cost/scr/cyq.py`（QuantsPlaybook / 广发证券多因子 alpha #27）
- **赢筹定义**：`get_cyqk_c() = get_winner(close)` = 当前收盘价以下的筹码累计占比
- **算法步骤**：
  1. 每日成交量按三角分布（默认）或均匀分布映射到 `[low, high]` 价格区间
  2. 按换手率衰减模型累积历史 N 日（默认 80 天）筹码分布：
     ```
     cumpdf_i = cumpdf_{i-1} * (1 - turnover_i) + curpdf_i * turnover_i
     ```
  3. 归一化后取 close 以下的累计比例

### 已发现的严重问题

| # | 问题 | 严重程度 | 影响 |
|---|------|---------|------|
| 1 | **`float_shares.parquet` 仅覆盖 100 只**股票，其余 5,400+ 只使用硬编码默认值 100 亿股 | **P0** | turnover_rate 被严重低估（大盘股 turnover 虚低，小盘股 turnover 虚高），直接导致筹码衰减速度完全失真。对小盘股影响可达 100 倍量级，历史筹码几乎不衰减，策略信号完全失效 |
| 2 | 分钟线使用**不复权**数据（`dividend_type=none`），但赢筹计算需要复权价格才能正确反映历史成本 | **P0** | 除权日价格跳变会导致筹码分布向低价区集中，赢筹被系统性高估。QMT 分钟线不支持复权，需用 `hybrid_chip_distribution`（日线复权定框架 + 分钟线做日内微调）折中处理 |
| 3 | 历史窗口固定 **80 天**，而同花顺/通达信通常使用 **100 天**或更长窗口 | P1 | 短期筹码权重差异，对波动大的股票影响显著。先做敏感性分析，仅在敏感股票占比 >20% 时才投入参数调优 |
| 4 | 换手率衰减系数 **A=1.0** 为固定值，券商可能使用不同的衰减模型（如半衰期模型） | P1 | 历史筹码衰减速度不同。同窗口长度策略：先修 P0，再做敏感性分析，按需调优 |
| 5 | 日内分布假设为**三角分布**（peak 在 close），而实际成交分布更接近真实量价 | P2 | 已通过分钟线直方图部分缓解 |
| 6 | **无任何与券商的外部交叉验证**——已有的 `verify_chip_factor_consistency.py` 只对比 daily vs minute 内部一致性 | P1 | 无法确认绝对精度，仅有相对一致性。低成本替代：先选取 5 只公认筹码集中/分散股票做常识性人工判断，快速发现量级错误 |

## 第二阶段：执行方案（两种路径）

### 方案 A：算法修复 + 理论偏差分析（推荐先执行）

**目标**：修复已知的本地算法问题，并从公开资料推断与券商的理论偏差。

**任务清单**：
1. **复权一致性修复**
   - 确认赢筹计算应使用**前复权**日线数据（`dividend_type=front`）
   - **责任点落在数据读取/下载层**，而非 `compute_chip_factors`：核查 `oskh_data/reader.py` / `oskh_data/downloader.py` 在读取日线时是否显式传入 `adjust_type='front'`（`backtest/stock_data_reader.py` 仅为兼容重导出，不作为主核查点）
   - **快速核查方法**（Git Bash / WSL）：`grep -rn "read_stock\|scan_stocks" backtest/ oskh_data/ | grep "period='1d'"`，确认所有日线读取调用均携带 `adjust_type='front'`
   - **Windows 等价命令**（PowerShell / ripgrep）：`rg -n "read_stock|scan_stocks" backtest/ oskh_data/ | rg "period='1d'"`
   - **注意**：上述 grep/rg 仅匹配显式传参 `period='1d'` 的调用。需人工复查未显式传 period 的 `read_stock`/`scan_stocks` 调用——这些调用使用默认 `period='1d'`，同样需要确认 `adjust_type` 参数
   - 评估分钟线（`dividend_type=none`）用于日内直方图时，对最终赢筹的系统性影响
   - **混合方案实现路径（已有代码，需验证）**：`hybrid_chip_distribution()` 已合并到 `backtest/chip_algorithm.py:287-344`，逻辑为：历史 79 天日线用三角 PDF 定框架 + 当日 240 分钟用实际量价直方图做日内微调。需验证该路径在 backtrader 中是否正确调用
   - **P0 #2 关闭标准**：运行 `verify_chip_factor_consistency.py` 确认日线 front 复权路径与分钟线 none 路径的 `cyqk_c` Pearson r > 0.85，且**按日期分组的 r 不低于 0.75**（防止总体 r 高但某些除权日/极端波动日塌陷被掩盖）。至少覆盖 20 个交易日切片。**允许失败切片上限不超过 10% 交易日**（即 20 个切片中最多 2 个低于 0.75），比单一最小值更抗噪——偶尔的极端交易日可能因 QMT 数据瞬时异常导致，不一定是算法问题（若当前基线未知，先跑一次获得基线后再定阈值）

2. **窗口长度敏感性分析**
   - 选取 20 只代表性股票（大盘/中盘/小盘/高波动/低波动各 4 只）
   - 分别用 60/80/100/120 天窗口计算 `cyqk_c`
   - 观察窗口长度对赢筹值的影响幅度
   - **策略**：仅在敏感股票占比 >20% 时才投入时间做参数调优，否则记录差异、接受即可

3. **理论偏差推断**
   - 调研通达信/同花顺筹码分布的公开算法参数（流通股本口径、窗口长度、衰减模型、复权方式）
   - 对比本地参数，列出所有已知差异点

**交付物**：
- 敏感性分析报告（窗口长度、复权方式对赢筹的影响）
- 理论偏差清单（本地 vs 券商的算法参数差异）

### 方案 B：样本对比验证（量化实际偏差）

**目标**：选取样本股票，将本地计算值与券商客户端显示值进行实际对比，量化偏差。

**前置条件**：需要确定"券商基准值"的获取方式。

**任务清单**：
1. **确定基准数据源并建立对齐协议**

   #### 基准分层（两级，不卡在"等一个可能不存在的接口"）

   **一级基准（必须）——本地自动化对照集**：
   - QMT 行情数据（`download_history_data2` / `get_market_data_ex`）+ 本地算法（`chip_algorithm.py` + `cyq.py`）
   - 完全可复现：固定代码版本 + 固定输入数据版本 + 固定参数，任何一次跑出来的结果应在统计量上一致（均值/标准差/分位数变化 < 0.1%），数值容差一致（abs diff < 1e-6）。不要求逐 bit 一致——DuckDB/NumPy/Numba 跨版本或不同 CPU 指令集下浮点末位可能正常漂移
   - 这是**日常评估的主基准**。在方案 B 的第一轮（修复前）和第二轮（修复后）之间，用它量化方案 A 的修复效果

   **二级基准（可选）——外部独立 API**：
   - 仅当满足以下条件时才作为 MAE/RankIC 参照物：① 数据源明确提供筹码/获利盘字段（不是推算值）② 网络可达 ③ 字段语义与本地算法对齐
   - 不要卡在"等一个可能不存在的接口"——二级基准是锦上添花，不是阻塞项

   #### 数据源技术评估（2026-05-17 实测）

   | 路径 | 方案 | 筹码字段 | 评估 |
   |------|------|---------|------|
   | QMT/miniQMT | `xtdata` 内置函数 | ❌ 无 chip/winner/cyq/cost | `dir(xtdata)` 仅含 `get_divid_factors` / `gen_factor_index`；`hasattr(xtdata, 'get_stock_factor') == False` |
   | AKShare | `ak.stock_cyq_em(symbol, adjust)` | ✅ 获利比例/平均成本/90%70%成本区间与集中度 | 底层依赖东方财富 `push2his.eastmoney.com`，接口字段天然对齐前复权 + 交易日精度 |
   | TuShare | 需注册 + Token | 部分覆盖 | 备选，筹码分布覆盖不如东方财富 |
   | 人工截图 | 同花顺/通达信客户端 | ✅ 获利比例 | 仅作 sanity check（5-10 只），不纳入主评估 |

   - curl_cffi 浏览器 TLS 指纹伪装（chrome120/124、edge101、safari17_0）
   - IP 直连（DNS 解析 IP `117.184.40.129` + 2 个 CDN 备选 IP）

   **二级基准数据获取（网络条件具备后）**：

   #### 基准对齐协议（必选项，否则 MAE/相对误差无意义）

   | 维度 | 规则 |
   |------|------|
   | 采样时点 | 统一使用**收盘后**数据（避免盘中快照与收盘值不一致） |
   | 复权口径 | 本地与基准均使用**前复权**收盘价 |
   | 取值精度 | 赢筹率保留 **4 位小数**（如 `0.7234`）；截图时若客户端显示百分比保留两位（如 `72.34%`），统一换算为 `0.7234` 再入库 |
   | 日期对齐 | 本地计算截面日期与基准日期**必须为同一交易日**，跨日对比无效 |
   | 窗口对齐 | 若已知基准使用 100 天窗口，本地同步切换为 100 天后再对比 |
   | 流通股本 | 本地使用补全后的真实 `float_shares`，若基准使用其他口径需记录差异

   #### 人工基准降级路径（仅在二级基准不可用时启用，仅做 sanity check）

   - 从同花顺/通达信客户端手动截图，**最多 5-10 只**，不纳入主 MAE/RankIC 评估
   - 截图统一归档至 `docs/investigation_reports/screenshots/{date}/{symbol}_{platform}.png`
   - 样本数据强制记录元数据字段：`platform` / `client_version` / `capture_time` / `symbol` / `trade_date`
   - **双录入复核 + 仲裁**：同一截图由两人独立录入；差异 > 0.002（约 0.2%）则标记为不可信，**剔除该样本**（不纳入统计）。不引入第三人仲裁——双录入不一致的样本本身就说明截图可读性或录入标准有问题，与其仲裁猜测，不如丢弃
   - 人工截图读数误差约 ±0.005，仅用于发现量级错误（如"明明是地量横盘，赢筹率却说 95%"）

   #### 阈值演变策略

   | 基准条件 | MAE 关闭阈值 | MAE 记录决策阈值 | RankIC 门槛 |
   |---------|------------|----------------|------------|
   | 一级基准（本地自动化对照集） | —（内部一致性，不设外部 MAE 要求） | — | — |
   | 二级基准（外部 API，样本 < 30 截面点，或含人工截图） | < 5% | > 10% | > 0.6 |
   | 二级基准（外部 API，样本 >= 50 截面点，纯自动化，稳定运行 2 周） | < 3% | > 7% | > 0.7 |
   | 仅人工截图（无二级基准） | 不做 MAE 关闭，仅 sanity check 通过即可 | — | — |

   > 阈值收紧的前提是二级基准本身稳定、可复现。不要在基准数据源还在波动时收紧阈值。
   > 后续接入外部 API 成功后：**连续两周数据采集稳定**（无断日、无异常空值、无字段变更）后，自动切换更严格阈值行（3%/7%/0.7），避免人为忘记收紧。

2. **样本选取**
   - 覆盖不同特征：大盘蓝筹、小盘成长、近期大涨、近期大跌、横盘整理、新股
   - 每只股票选取 3-5 个不同日期的截面数据
   - **最少保证 30 个截面点**（如 10 只 × 3 日期，或 15 只 × 2 日期），以满足停损条件 N >= 30 的要求

3. **本地计算（分两轮，量化修复效果）**
   - **第一轮（修复前）**：使用当前未修复算法（旧 float_shares + 当前复权配置）计算每只样本股的 `cyqk_c`，建立现状基线
   - **第二轮（修复后）**：使用方案 A 修复后的算法（补全 float_shares + 统一 front 复权）重新计算
   - **归因纯净约束**：两轮必须使用**同一 symbol + 同一 trade_date** 对照；外部基准快照必须冻结为同一收盘时点，避免市场自然波动混入修复收益
   - **结果可复现快照**：固定并记录输入数据版本——`float_shares.parquet` 文件哈希/时间戳、日线/分钟线数据区间（如 `period=1d/front: 2024-01-01~2026-05-15`），写入报告附录，防止后续数据更新污染结论
   - **对比期数据冻结**：方案 B 两轮对比期间（从第一轮启动到第二轮完成），**禁止执行任何数据回填/补录操作**（`oskh_data.backfill`、`oskh_data.downloader`、DuckDB 增量更新）。即使哈希可追溯，中途数据变更也会在 ROI 归因中引入噪声——冻结比事后解释更便宜
   - 两轮差值即为方案 A 的 ROI，避免"修了但不知道修了多少"

4. **偏差量化**
   - 计算 Pearson r、MAE、相对误差
   - 按市值/行业/波动率分组，分析偏差模式
   - 定位最大偏差的来源（流通股本？复权？窗口？）

**交付物**：
- 样本对比数据集（本地值 vs 券商值）
- 偏差统计报告（r、MAE、分组分析）
- 根因定位结论

## 第三阶段：长期建议

1. **建立 float_shares 定期更新机制**（每月/每季度从 QMT 同步）
2. **引入历史流通股本**（`free_float_shares.parquet`）——除权送转时流通股本会变，用固定值计算历史 turnover 会失真。**当前版本接受静态股本的误差**；仅在 float_shares 静态值被证明导致显著 P&L 偏差时才考虑引入历史股本（维护成本高，做错了比不做更危险）
3. **分钟线筹码分布使用前复权校正**（`adj_minute_chip_distribution` 已实现但需验证）
4. **建立与券商的自动化回归测试**（如每周抽样 50 只股票，对比本地 vs 同花顺）
5. **考虑引入换手率半衰期模型**（`turnover_coefficient_ops.py` 中的 ARC/VRC/SRC/KRC）作为补充验证

## 调查终止条件（停损，避免无底洞）

- **关闭条件（二级基准可用时）**：所有 P0 修复后，样本量 **N >= 30 个截面点**，且覆盖**大/中/小盘三组**后，同时满足：
  - MAE < 5%（vs 至少一个外部基准）
  - **Spearman RankIC > 0.6**（排序稳定性门槛，防止"数值接近但选股顺序已失真"）
  → 关闭调查。避免小样本（5–10 只、单一市值风格）误判通过
- **关闭条件（降级路径，外部基准不可用时）**：所有 P0 修复后，满足以下全部条件即可关闭：
  ① 一级基准两轮对比确认修复有效：在已知异常样本（小盘高换手、近 30 日有除权）上，修复后 cyqk_c 中位绝对变化 > 5%（证明修复有实质影响），且全样本不出现系统性反向偏移（修复后 cyqk_c 均值 ± 方向应与 P0 修复理论方向一致：float_shares 修复→小盘股赢筹率下降、复权修复→除权股赢筹率下降）。满足此量化条件即视为"变化方向符合预期"，避免不同成员口径不一
  ② 人工 sanity check（5-10 只，覆盖大/中/小盘）无量级错误（如"跌 50% 但赢筹率 95%"）
  ③ 算法与理论偏差清单无未解释的 P0/P1 差异
  → 关闭调查。外部基准不是阻塞项——流程必须可降级可闭环
- **记录决策条件**：MAE > 10% 或 RankIC < 0.4，定位到具体参数并记录，由交易决策者判断是否接受
- **反直觉保护**：若修复后 MAE **反而增大**，不自动判定修复失败。先核查外部基准的浮筹口径/复权方式是否与本地一致；若不一致，记录差异即可，不要求 MAE 收敛。防止把正确的修复回滚成错误状态
- **硬停损**：无论结果如何，总耗时上限 **3 人天**，超时后输出阶段性报告并暂停
- **P0 未关闭禁止上线**：若调查停在"已知 P0（float_shares 缺失/复权错误）仍存在"状态，**明确禁止用于生产交易决策**，防止"先跑起来再说"的不可逆风险
- **上线前自动拦截脚本**（机器可执行，不依赖人工记忆）：发布前必须通过 `scripts/diagnostics/preflight_chip_diagnosis.py`，检查项包括：
  - `float_shares.parquet` 覆盖率 >= 99%
  - 日线 `period=1d/dividend_type=front` 数据存在且非空
  - 分钟线 `period=1m/dividend_type=none` 数据存在且非空
  - 样本量 >= 30 截面点（从 `config/chip_diagnosis.yaml` 读取样本列表）
  - `config/chip_diagnosis.yaml` 的 SHA-256 哈希已写入本次报告元数据（保证"执行—报告"链路闭环，防止参数被改但报告未更新）
  - 任一失败即退出非零码，阻断发布。**该脚本默认由 CI 流水线或发布命令强制触发**，不依赖人工记得执行——脚本存在但没人跑等同于不存在
